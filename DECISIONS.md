# EventNexus decision log

Rows are grouped roughly by phase. Decisions made after seeing a result are marked **post-hoc** with the reason; the rule that was set in advance keeps its original verdict.

| Decision | Choice | Why |
|---|---|---|
| Scope | Karachi: any city spelling, plus Sindh events inside Karachi's coordinate box (about 2,800 events across all years) | Karachi alone has plenty of events; district-named events are included, Hub (Balochistan) is not |
| Time window | 2000 to 2020 (about 1,650 events) | Incident summaries exist only from 2000; the 1990s have almost no text and mostly unknown perpetrators |
| Main focus | Cross-event analysis, not information extraction | GTD is already structured; the value is in connecting events |
| Graph database | Local Neo4j Desktop, database `eventnexus-db` | Offline-capable, native vector index, built-in browser |
| Data format | GTD converted once to Parquet; notebooks for exploration, scripts for repeatable steps | Fast loading on an 8 GB machine; reproducible pipeline |
| NER | GLiNER (medium) was evaluated against a rule-based extractor for place extraction and not used; spaCy was installed as a baseline but not needed | The rules matched GLiNER's precision and found more places (see the Area extraction row) |
| Embeddings | all-MiniLM-L6-v2 | Small and fast on CPU |
| Classifier base | distilbert-base-uncased | Used for the scope guard only if it beats logistic regression on MiniLM embeddings (see the Scope guard row); light enough for a 6 GB GPU |
| Serving | The fine-tuned model is shipped as a GGUF (Q8_0, 7.97 GB) on Hugging Face Hub, because GitHub rejects files over 100 MB. The app has one OpenAI-compatible client, with the server address and key in .env (LLM_URL, LLM_API_KEY); only the server location differs. On a capable PC the server is local (llama.cpp or Ollama, fully offline). Without one, the author runs the same GGUF with llama-server in a Kaggle CPU notebook behind a cloudflared quick tunnel (free, the URL changes at every start) and updates LLM_URL. No third-party hosted model is used (Gemini was removed entirely). Free-cloud options considered and not chosen: Oracle Always Free ARM CPU, Modal, HF Spaces, Cloudflare Workers AI, Lightning. The test set is scored on the quantized GGUF that ships. | Anyone can run offline, and the author can demo without a GPU PC. A scored file that differs from the shipped file would say nothing about what users run |
| Fine-tuned query model | A small model fine-tuned with QLoRA writes Cypher for the open lane, routes to the fast lane, or refuses. Winner of the bake-off: Gemma 4 E4B (google/gemma-4-E4B-it) | Replaces the optional ~1B query-picking model; the headline trained model |
| Frontend | Plain HTML, CSS, JavaScript with D3, served by FastAPI | No Node build step; works offline |
| PyTorch | Installed per machine, not in requirements.txt | CPU here, CUDA on the GPU machine |
| Data privacy | Raw and processed data are not tracked by git | GTD terms of use; file size |
| Area from text | Neighbourhoods are extracted from location and summary text, not coordinates | 1,627 of 1,664 events share one city-centre coordinate |
| Columns kept | 32 of 135 (identity, place, actor, method, target, outcome including perpetrator casualties, cross-event hints, text, evidence) | Chosen for linking events, describing them, or evidence; `nkillter` and `nwoundte` were added so severity can exclude attackers; the rest are mostly empty or redundant |
| Unknown is not a link | Values labelled "Unknown" (and generic groups) never create shared-attribute links in the graph | Two unknowns don't mean the same thing |
| Graph questions | 15 questions in 5 tiers (lookup, cross-event patterns, multi-hop chains, provenance, similarity); 12 of them are cross-event | The schema is built backwards from the questions, so every structure earns its place |
| Graph nodes | Event, Group, AttackType, WeaponType, TargetType, TargetOrg, Source, Area and Locality (the last two come from place extraction in Phase 4) | These are the things events connect through |
| Unknown means no edge | An event with an unknown weapon, target or group simply has no edge of that kind; the text value stays on the event for display | Makes "Unknown is not a link" structural, not just a query habit |
| Confidence on edges | `claimed` and `uncertain` are stored on the ATTRIBUTED_TO edge | Confidence belongs to the link between an event and a group, not to the group |
| Derived cross-event links | SAME_ACTOR_NEARBY, SAME_SOURCE, SAME_MO_LOCAL, FOLLOWED_BY, SIMILAR_TO; each stores rule, strength and evidence | Every link can explain why it exists, which answers "why are these linked?" |
| Same-actor window | 30 days, with gap_days stored on each edge (236 pairs within 7 days, 632 within 30, 1,446 within 90) | Captures campaign waves without a flood of loose links; other windows stay queryable |
| Shared sources link events | 411 citations are shared by 2 or more events, covering 664 events (40%); SAME_SOURCE uses citations shared by 2 to 10 events (none exceeds 7, so nothing is excluded) | Reaches the 80% of events with an unknown actor |
| GTD related is evaluation only | GTD_RELATED pairs are never used to build links, retrieve results or train models | Prevents a circular evaluation |
| `multiple` is a property only | Not used as a link rule or model feature | It is tied to GTD's own relatedness judgement |
| Rule parameters | Windows, thresholds and validator limits live in dictionaries in src/config.py (GRAPH_RULES, CLUSTER_RULES, VALIDATOR_RULES, FAST_DEFAULTS) | Tuning never means rewriting rules |
| Placeholder organisations | "Not Applicable" and "Civilian(s)" create no TargetOrg node | They mean no organisation, and would form false hubs (140 events) |
| Organisation aliases | Spelling variants of the same organisation are merged (MQM, MQM-H, ANP, PPP, police) | Prevents one organisation being split across nodes and losing links |
| Rebuildable graph | `build_graph.py --reset` rebuilds the Phase 3 and 4 graph (running it twice gives identical counts). The Phase 5 steps (embed_graph.py, similar_links.py, cluster_events.py) and components.py rerun on top of it, and check_graph.py verifies the result | Reproducibility. The reset also removes embeddings, SIMILAR_TO and clusters and leaves components.json stale, so the order matters |
| Source links reach the unknown actors | 607 SAME_SOURCE links connect 524 of 1,338 unattributed events (39%) | The cross-event value for the 80% with no named group |
| Fair evaluation of GTD pairs | GTD_RELATED is tested against text similarity alone, not against source or actor links | 115 of 118 GTD pairs are already linked by shared sources or same actor, so those links would make the test too easy |
| Area extraction method | Rule-based extractor with a gazetteer (names seen in 2+ events). GLiNER and a rules-then-GLiNER hybrid were evaluated and not used | One-shot test on 30 events: rules precision 0.95, recall 0.77 (0.95 on recurring places); GLiNER 0.95 / 0.69; hybrid identical to rules |
| Area definition | One primary Area per event at town or neighbourhood level. Sub-areas that roll up are kept as Localities. Recurring named facilities (consulate, embassy, dockyard, headquarters, airport, airbase, cantonment) count as Areas; roads, districts and police stations do not | Matches how the text names places and what can link events |
| One-event names are not Areas | A name seen in only one event does not become an Area node | It cannot link events; most remaining misses are one-off places |
| Area evaluation protocol | 60-event development set and a separate 30-event test set scored once; text-only labels by the author (single annotator) | Avoids tuning on the test set. Known limits: small sample, one labeller |
| Area roll-ups | A hand-written map folds sub-areas into their town (for example Mominabad into Orangi, Qasba Colony into SITE); places that only look nested (Pirabad and Qasba Colony, Gulistan-e-Jauhar and Gulshan-e-Iqbal) stay separate | Decided by the author from local knowledge; the text alone cannot tell nested from neighbouring |
| Districts and roads are not Areas | Karachi East, Central, South and West, and road names, are ignored | Too coarse or too linear to link events |
| Ambiguous names get no Area | "Bilal Colony" (two different places) is excluded | A shared name would create false links |
| Late extractor changes | Aliases, roll-ups, bare-location handling, the road and district exclusion and the two-level model came after the test set was scored | The test numbers describe the earlier version |
| Two-level places | Area (town level) is used for linking and counting; Locality (specific sub-area) is kept on every event and shown in detail views | Linking needs coarse groups, but users must still learn exactly where an event happened |
| FOLLOWED_BY forms chains | Each event links to the next event in the same Area if it comes within 7 days, not to every event in the window; the longest chain has 13 links, from 20 January to 24 February 2014 | Avoids tangles of links and supports questions about escalation sequences |
| SAME_MO_LOCAL rule | Same Area, same attack type, weapon type and target type (Unknown never counts), within 30 days; a same_locality flag marks events in the same locality (184 links) | Finds repeated methods in the same place |
| Chronology uses dates, not IDs | Ordering and time windows use the date fields; the eventid is only an identifier | GTD IDs can disagree with the date fields (event 201402100070 is dated 2014-02-08) |
| Embedding input | `summary_clean` only, embedded with all-MiniLM-L6-v2 and normalised to unit length; cached in `data/processed/event_embeddings.npz` with the event IDs saved beside the vectors | The longest summary is 217 word-pieces against a 256 limit, so nothing is truncated. Unit length makes cosine a dot product, and the IDs prevent vectors drifting out of row order |
| Duplicate records | The 9 `dup_group` pairs (identical `summary_clean`) are excluded from SIMILAR_TO before ranking; the events stay in the graph | Identical text scores 1.0 whether the pair is a twin record or two incidents with templated wording, so the link reflects the wording and not a cross-event finding. Masking before ranking keeps each event's 5 slots for real neighbours. Cost: the templated-wording incidents lose a similarity link; actor, source and method links can still connect them |
| SIMILAR_TO rule | Top 5 embedding neighbours by raw cosine, cut-off 0.85, kept only when mutual (each event is in the other's top 5). 928 links, 784 events (47%), maximum 5 links per event | Random pairs reach 0.70 at their 90th percentile, so low cut-offs link unrelated events. Without the mutual rule, generic texts became hubs (maximum 40 links, 86 events above 10); a cap of 10 was arbitrary and kept the generic links |
| SIMILAR_TO properties | `strength` (raw cosine), `gap_days`, `same_area` (only when both events share an Area), `rule`, `evidence` | Embeddings capture pattern, not campaign. Time and place stay filterable at query time instead of adding a second threshold. Only 13% of links are within 30 days and 11% in the same Area |
| Cut-off set without GTD_RELATED | 0.85 came from the score distribution and a manual read of sampled pairs | Keeps the GTD pair test uncircular |
| GTD_RELATED test result | One run, text similarity only (111 pairs with different text): mean percentile rank 0.968 among all pairs, median 0.997; 57% of pairs above the 0.85 cut-off, 50% linked by SIMILAR_TO | The baseline is all pairs, which includes different years and attack types, so the rank is easier to reach than chance suggests. Small sample, one run |
| Clustering | UMAP to 5 dimensions, then HDBSCAN (minimum cluster size 10): 31 clusters, 20% noise. A separate 2-D UMAP is used only for the map | Clustering is more reliable in a middle-dimensional space than in 2-D. HDBSCAN chooses the number of clusters itself and leaves one-off events as noise |
| Clusters are a property, not a link | `Event.cluster` is an integer, left unset for noise. Clusters create no edges | A cluster says an event is of a type, not that two events are connected. Applies "Unknown is not a link" to noise |
| Clusters overlap the GTD fields | Most clusters are 94 to 100% a single weapon type. They are kept as a theme grouping, mainly for the clusters that split by target or time window (for example police shootings, religious figures, hostage-taking) | Reading the clusters showed the broad split repeats the weapon field, so they are not presented as findings about campaigns |
| Map data lives outside the graph | 2-D coordinates and cluster ids are saved in `data/processed/event_map.json` | Keeps display data out of the graph; the app serves the file directly |
| Cluster numbers are unstable | Cluster ids change if parameters or library versions change; no query may hard-code one. Naming clusters is left to Phase 8 | Names should be chosen after seeing how the QA layer uses them |
| Severity | Victims killed (`nkill` − `nkillter`), then victims wounded (`nwound` − `nwoundte`). Unknown is not zero: events without `nkill` are skipped, and a missing perpetrator count means the total is used and flagged | GTD totals include attackers. In 2016-2020 the third event by raw `nkill` had only attackers killed |
| Vector search syntax | `db.index.vector.queryNodes` is used in `embed_graph.py` and in queries Q14 and Q15 of the query library. Neo4j deprecated it in 2026.04 in favour of the `SEARCH` clause. It still works on 2026.09; migration is planned after the core app works | A deprecation warning appeared on the rebuild |
| Event ids are internal | Users never type or see event ids. Queries return ids in underscore columns, which the app removes. Events are reached by description, previous results or graph clicks | Ids mean nothing to users and expose the database |
| Relative dates | "Last N years" counts back from the end of the data (2020-12-22), and the answer says so. Requests wholly outside 2000-2020 are refused with a reason | Counting from today would return nothing |
| Link windows | `SAME_ACTOR_NEARBY` and `SAME_MO_LOCAL` answer up to 30 days, `FOLLOWED_BY` up to 7. Longer windows use computed queries (Q3b, Q4b) | Stops a longer window being silently cut to 30 days |
| Coordinated attacks | Q5 returns the gap, same area, shared sources and GTD's `multiple` flag for display, and defines no "coordinated" rule | There is no independent rule, and `multiple` stays display-only |
| Attribution labels | claimed, suspected, and "attributed, not flagged suspected" | GTD has no "confirmed" flag |
| Base-model bake-off | One recipe for all candidates (see the Training recipe row), no per-model tuning. Winner: highest dev execution accuracy after fine-tuning. A model with a larger 4-bit size must win by at least 5 points; smaller gaps go to the lighter one. Hard filters are in the next row | One recipe means gaps come from the model, not the tuning. Dev has 65 to 70 answerable questions, so 5 points is 3 to 4 questions and is inside the noise: a tie-break rule, not a significance test |
| Bake-off hard filters | (1) Trains with QLoRA on one Kaggle T4 (16 GB, fp16) with no NaN or inf loss in the first 300 micro-steps (micro-steps, because 962 samples at an effective batch of 8 give only 121 optimizer steps). (2) Peak VRAM at most 14 GB in 4-bit with the real prompt plus 256 output tokens. (3) Merges, converts to GGUF and loads in Ollama or llama.cpp. The measured 4-bit VRAM of the winner is published in the README as the minimum GPU. **Replaces the earlier filter** of at most 5.5 GB on a 6 GB GPU, which was dropped | The model must be trainable and servable on the author's free setup. Anyone with enough VRAM can run it offline; the 6 GB cap excluded models that train and serve well on a T4 |
| Bake-off candidates | Narrowed to Qwen2.5-Coder-3B-Instruct and Gemma 4 E4B (it). Dropped: Phi-4-mini, Qwen3.5-4B (QLoRA on its hybrid architecture was unverified) and Qwen2.5-Coder-7B (about 5 h per run). Instruct variants only | Two models fit the free GPU quota: each run takes about 2.5 h, and Kaggle gives about 30 GPU hours a week (unverified figure) |
| Training recipe | QLoRA nf4 with double quantization and fp16 compute. LoRA rank 16, alpha 32, dropout 0, on q, k, v, o, gate, up and down (Gemma: text tower only). Learning rate 2e-4, 2 epochs, seed 42, micro-batch 1 with 8 accumulated, 5% warmup then linear decay, AdamW, gradient clip 1.0, adapters in fp32 with a gradient scaler, gradient checkpointing. Loss on reply tokens only; the reply ends with the chat template's own end-of-turn token (not eos_token). Logits are computed only for reply positions. Training aborts on a first loss above 6 or NaN/inf in the first 300 micro-steps. Generation cap: fixed max_new_tokens 512 from v3 on (the v2 cap, longest training reply plus 40, truncated one reply per model) | bf16 is emulated on the T4, so fp16 with a scaler is used. Computing logits only for reply positions cut Qwen's peak memory from 8.55 to 5.62 GB |
| Two lanes | Fast lane: library queries run with app-filled parameters. Open lane: model-written Cypher in a read-only transaction, no CALL. The model routes and replies CYPHER, REFUSE or FAST. FAST covers Q1 (details or sources of one event, at least 1 event in context), Q8 (at least 1), Q10 (at least 2; also answers why two events are linked), Q14 (at least 1) and Q15 followed by a group from the list. Q0b (the event finder, which also answers ranking questions), Q2 to Q7, Q9, Q11 and Q13 are open lane. The app sets k, min_cosine and limit, and Q10 runs the component check first (see the Path bound row). Validator: LIMIT required and at most 100 (50 for lists); 10 s timeout; variable-length patterns only on FOLLOWED_BY, directed, of any length (each event has at most one successor in its area, so chains are linear and the longest has 13 links; Q9 needs an unbounded pattern); CONTAINS only on location, summary_clean and TargetOrg name; FAST accepted only as Q1, Q8, Q10, Q14 or Q15, and Q15 only with a group in the list; Neo4j notifications (for example 03N90) are not failures, only errors are. Aggregation questions (counts, totals, averages, group-by tables, rankings) are open lane too; they have no FAST form and cannot be promoted. | Measured on the dev PC: shortestPath between five pairs (two from the highest-degree event at distance 6 and 7, one at distance 21, two hubs 4 apart, and a cross-component pair) took 22 to 265 ms on the first run and 4 to 9 ms on the second. An earlier single figure of 4,327 ms was not reproduced (cold start suspected, not proven). 3-hop expansion from the 5 busiest events reached 78 to 200 events and 5,262 to 6,558 paths. Counting every path of up to 6 links from the busiest event (16,765,630 paths) took 3.7 s, and a sorted top 50 over paths of up to 5 links took 0.9 s, so enumeration needs no extra rule. The 10 s timeout stays as the ceiling, and a query that hits it returns a plain "too broad" message. Re-time these on the demo PC. Q8 and Q10 are FAST from the start because they need only event context and no text parameters, and open-lane patterns over the undirected link union return the same event many times and loop back to the start event (seen in the 5-hop test); Q8 is also the hardest library query for a small model to write (expected, not measured). Q1 joined FAST by the promotion rule (see the Promotion outcome row). The open lane never writes vector search, so moving to SEARCH cannot break training pairs |
| Metrics | Primary: execution accuracy, the share of answerable questions whose query returns the same result as the gold query: the same set of events when the gold returns events (underscore columns), otherwise the same rows on the gold's columns, each matched to a model column by value (names, column order and extra columns ignored; row order always ignored); for top-N questions the same N events, and gold must have no tie at the cut. Numbers such as an average are compared after rounding to 2 decimals. Test lists whose full result exceeds the gold LIMIT of 50: the model's rows must all belong to the full gold result (the gold without its LIMIT), with no duplicates, and there must be min(50, size of the full result) of them; on lists of 49 or fewer rows this is the same as the same-set rule. A single-event lookup is correct when its one returned row is the referred event. run_eval's execution accuracy counts only items whose expected type is Cypher. Secondary: valid-query rate (CYPHER outputs that pass the validator and run, over all CYPHER outputs); refusal reported as two numbers, refusals made when they should and questions wrongly refused. FAST counts only with the right query and group | One refusal accuracy would hide over-refusing; the list rule avoids marking a correct 50 of many wrong because of ordering |
| Dev and test sizes | Dev: 105 questions. 60 Cypher: five phrasings for each of Q0b, Q2 to Q7, Q9, Q11 and Q13, plus 10 aggregation questions (AGG) added by src/make_dev_agg.py. 30 FAST: Q1 5, Q8 5, Q10 10 (5 originally Q12), Q14 5, Q15 5. 15 should-refuse, including questions about "that event" with events=0. (Before the Q12 and Q1 relabels, dev was 70 Cypher / 20 FAST / 15 refuse.) Test: 60 questions written by 4 testers, labelled before the first run: 53 cypher, 2 FAST and 5 should-refuse (the plan was about 40, 10 and 10, so FAST and refusal results on the test set are reported as counts only) | Enough to rank models roughly; test intervals stay wide (see the Test set row) |
| Test set | Questions from at least 3 people other than the developer, none from an LLM, who get one paragraph describing the data and not the library or the prompt. The developer sets the CONTEXT line (events=N) for each question from its wording before the first run. Gold written before the first run. No question dropped or edited after any model sees the set. Any training question with MiniLM cosine of 0.85 or more to a dev or test question is removed, and the count is reported. Scored once. Gold is reviewed line by line before the first run. On 2026-10-26 the developer confirmed that no test question was written by an AI tool and that he reviewed all 60 gold lines. Items whose gold needs a property the prompt does not list (x031, x032), and items with an empty gold by design (x013, x044), are reported as separate subgroups, as are lists that reach the LIMIT of 50 (13 items), the "no link" probe x037, and the single-event items x004 and x049, which the model may route to FAST: Q1 (left unchanged on purpose); ambiguous readings (x023, x047, x053) are flagged in each item's note. The test file is not on Kaggle: its questions reach the model only through the tunnel. Frozen with git tag test-set-v1 | With 53 answerable questions a 95% interval on accuracy is about plus or minus 11 to 14 points, so only large gaps mean anything; results report intervals. Leaving x004 and x049 unchanged is the honest choice: changing a question because of how the model might route it would tune the test to the model |
| Fine-tuning success rule | On the test set, fine-tuned execution accuracy beats the untrained model's by at least 15 points and the paired difference passes a one-sided exact sign test at p below 0.05 (only questions where exactly one model is right). The untrained model gets the same prompt file, validator, client and server flags, with no few-shot examples. Both are scored as Q8_0 GGUF files: the fine-tuned merged model (see the Shipped file rows) against the untrained base google/gemma-4-E4B-it converted to Q8_0. The sign test uses the 53 Cypher items. If the rule fails, the report says fine-tuning did not help | 15 points is about 8 net questions of 53 (10 wins to 2 losses, for example); the sign test also has to pass: 9 wins to 2 losses passes, 8 to 2 does not. Scoring the shipped quantization on both sides keeps the comparison about what users run |
| Promotion to FAST | After the fine-tune of the bake-off winner, any open-lane query among Q0b, Q1 to Q7, Q9 and Q11 to Q13 with fewer than 4 of its 5 dev phrasings correct by execution is promoted to FAST. Dev set only, applied once. The lane map is frozen before the test run. A promoted query that needs text parameters was to be written FAST: Qn key=value, with the library's parameter names and validator checks on each value; **this form was not built** (see the Promotion outcome row). Q8, Q10, Q14 and Q15 are already FAST and take only event context or a group. The whitelist widens in the same change as the prompt and the training pairs | A query the model cannot write reliably is better served by the library. Changing the whitelist without the prompt and pairs would make the model emit forms the validator rejects |
| Promotion outcome | The rule triggered for Q1, Q3, Q4, Q7 and Q9 (and for Q12 before it was merged into Q10). Applied only to Q1: it takes only the $ref event, so FAST: Q1 needs no parameters. Not applied to Q3, Q4, Q7 and Q9: FAST has no parameter syntax for group, year, window or area, and promoting them with library defaults would silently drop the user's filter. They stay in the open lane and are reported as known limits; after the v3 retrain only Q3 (2/5), Q7 (3/5) and Q9 (3/5) stay under 4/5. **This departs from the pre-set rule (post-hoc)** | A wrong default answer that looks right is worse than an open-lane query that sometimes fails validation. The pre-set rule assumed a parameter form that was not built, and building it after seeing dev results would be a larger change than the rule intended |
| Q12 merged into Q10 | Q12 ("why are these two events linked") scored 0/5 in all four bake-off runs, because prompt rule 11 sends that wording to FAST: Q10. Q12 is merged into the Q10 route. The app's Q10 handler runs the direct links and shared sources first (the old Q12 query), then the component pre-check, then the shortest path of up to 6 hops. Dev items d051 to d055 became fast/Q10 (phrasings 6 to 10 of Q10); the 7 kept Q12 training pairs were relabeled FAST: Q10. **Post-hoc**; the prompt was not changed for this reason alone | Identical wording scored 0/5 for every model, so the fault was in the spec and not in the models. Keeping Q12 open-lane would have counted a routing conflict as model failure |
| Training data | About 10 to 15% of pairs are FAST examples. About 8% are aggregation pairs (AGG: counts, totals, averages, group-by tables and top-k rankings), because the testers asked many such questions and no library query covers them. Every pair carries the CONTEXT line (events=N). Pairs are never built from GTD_RELATED. Version v3: 518 raw pairs, 481 after the overlap filter (37 removed: 29 against dev, 8 against test), by type 331 Cypher, 75 FAST (15.6%) and 75 refuse; the 36 AGG pairs counted in v2 sit inside the Cypher group (not re-counted for v3). Regeneration after the prompt change was deterministic: a diff showed only the intended ids changed, because the relabel runs after generation and before the shuffle | The model must learn when to route, and the context line is what it routes on. FAST share rose above the planned range when Q1 and Q12 pairs were relabeled |
| Place-fallback test | Run first with hand-written Cypher, no model: 10 road or landmark names taken from events with no Area, chosen before looking at results, up to 5 events each. Correct = the event text names the place as where the incident happened (a mere mention does not count), labelled by the developer. Keep the fallback if at least 80% of returned events are correct and at least 40 events came back (the 40-of-50 rule). 5 invented names must each return no rows. If it fails, names in neither list are refused. **Result (2026-10-22, `src/place_fallback_test.py`, `results/place_fallback.json`): FAIL on the rule above.** 12 events came back (need 40); 12 of 12 were judged correct; all 5 invented names returned no rows. **Decision made after seeing the result:** keep the fallback anyway. Every fallback answer shows the stored `location` and `summary_clean` text of each event, so the user can check the match. Revisit if test-set questions show wrong or misleading fallback matches | The fallback pattern is about the data, not the model, so it can be tested before any GPU work. One labeller, as in the area evaluation. The count rule measured coverage, not accuracy: most roads and landmarks appear in one event, so 10 names could hardly reach 40 of 50, and I set that threshold without checking. The sample is small (12 of 12 gives a Wilson lower bound of about 0.76), so accuracy is shown only roughly. The keep decision is post-hoc and the pre-set rule's verdict stays FAIL. The model evaluation is untouched: prompt and test set are unchanged |
| Scope guard and link scorer | Guard: in, second priority after the headline model (not started). Logistic regression on MiniLM embeddings first; DistilBERT only if it beats it by at least 5 points of accuracy in 5-fold cross-validation on the training questions. Pass: on the test set at least 4 of the 5 should-refuse questions caught and at most 5 of the 55 other questions blocked; with only 5 refusals this is a coarse check and is reported as counts. Link scorer: out of Phase 6 | The guard is a second check on refusals and the only place DistilBERT could earn its slot. The link scorer needs about 200 hand-judged links and was the first cut |
| Names outside the lists | Places not in the Area or Locality lists are searched in location and summary_clean with CONTAINS, and the query returns 'text' AS place_match; the answer always shows each returned event's stored location and summary_clean text and says a text match may be incomplete ("no event text mentions X, and the data has no coordinates to search by" when nothing is found). Organisations (380, not listed) are matched on the TargetOrg node with CONTAINS on one distinctive word, returning 'text' AS org_match and o.name AS org_name. Groups not in the 39 are refused. Bare "Taliban" is refused with a question; ISIS and Daesh map to the Khorasan Chapter of the Islamic State and the answer names the full group. "Karachi" or "Sindh" alone is not a place filter | Roads, courts and landmarks are what people type and cover the 26% of events with no Area. Attribution comes only from the ATTRIBUTED_TO edge, so groups get no text fallback. The place fallback failed its pre-set count rule and was kept by a later decision, with the text shown so a wrong match is visible (see the Place-fallback test row) |
| Open-lane query conventions | Filter on the Event properties attack_type, weapon_type and target_type; use the type edges only to group across events (Q6, Q11). Severity ranks by victims killed, then victims wounded, with coalesce on wounded (Cypher sorts null first in descending order). | Gold queries | Dev gold queries are open-lane forms of the library queries: literals instead of parameters, LIMIT added (50 for lists), no CALL (Q11 is split into area and organisation variants), no multiple column, and no list columns, so scoring compares events or scalar values. Aggregation (AGG) gold returns a count, a sum, an average, a group-by table or a top-1 row; severity is computed in WITH and groupings by type use the type edges. Dev lists are chosen so the full result has 1 to 49 rows and top-N questions have no tie at the cut. Test gold follows the same forms plus a few custom queries for the testers' wording (a mosque or shrine text search, repeated incidents in the same month); it may reach the LIMIT of 50 (scored by the list rule) or be empty by design, and top-N questions still have no tie at the cut. Slot values come from the graph, and every gold query is validated and executed by src/make_dev.py, src/make_dev_agg.py and src/make_test.py. The test gold was drafted by the assistant and then reviewed line by line by the developer | A gold query that the validator would reject, or that the LIMIT cuts without a rule for it, would make scores meaningless |
