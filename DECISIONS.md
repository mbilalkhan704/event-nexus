# EventNexus decision log

| Decision | Choice | Why |
|---|---|---|
| Scope | Karachi: any city spelling, plus Sindh events inside Karachi's coordinate box (about 2,800 events across all years) | Karachi alone has plenty of events; district-named events are included, Hub (Balochistan) is not |
| Time window | 2000 to 2020 (about 1,650 events) | Incident summaries exist only from 2000; the 1990s have almost no text and mostly unknown perpetrators |
| Main focus | Cross-event analysis, not information extraction | GTD is already structured; the value is in connecting events |
| Graph database | Local Neo4j Desktop, database `eventnexus-db` | Offline-capable, native vector index, built-in browser |
| Data format | GTD converted once to Parquet; notebooks for exploration, scripts for repeatable steps | Fast loading on an 8 GB machine; reproducible pipeline |
| NER | GLiNER (medium) was evaluated against a rule-based extractor for place extraction and not used; spaCy was installed as a baseline but not needed | The rules matched GLiNER's precision and found more places (see the Area extraction row) |
| Embeddings | all-MiniLM-L6-v2 | Small and fast on CPU |
| Classifier base | distilbert-base-uncased | Used for the scope guard only if it beats logistic regression on MiniLM embeddings (see the Scope guard row); light enough for a 6 GB GPU |
| LLM | Provider switch: Gemini API in development, local Ollama model for offline mode | Speed and quality now, offline demo later |
| Fine-tuned query model | A small model fine-tuned with QLoRA writes Cypher for the open lane, or refuses | Replaces the optional ~1B query-picking model; the headline trained model |
| Frontend | Plain HTML, CSS, JavaScript with D3, served by FastAPI | No Node build step; works offline |
| PyTorch | Installed per machine, not in requirements.txt | CPU here, CUDA on the GPU machine |
| Data privacy | Raw and processed data are not tracked by git | GTD terms of use; file size |
| Area from text | Neighbourhoods are extracted from location and summary text, not coordinates | 1,627 of 1,664 events share one city-centre coordinate |
| Columns kept | 32 of 135 (identity, place, actor, method, target, outcome including perpetrator casualties, cross-event hints, text, evidence) | Chosen for linking events, describing them, or evidence; `nkillter` and `nwoundte` were added so severity can exclude attackers; the rest are mostly empty or redundant |
| Unknown is not a link | Values labelled "Unknown" (and generic groups) never create shared-attribute links in the graph | Two unknowns don't mean the same thing |
| Graph questions | 15 questions in 5 tiers (lookup, cross-event patterns, multi-hop chains, provenance, similarity); 12 of them are cross-event | The schema is built backwards from the questions, so every structure earns its place |
| Graph nodes | Event, Group, AttackType, WeaponType, TargetType, TargetOrg, Source, Area and Locality (the last two come from place extraction in Phase 4) | These are the things events connect through |
| Unknown means no edge | An event with an unknown weapon, target or group simply has no edge of that kind; the text value stays on the event for display | Makes "Unknown is not a link" structural, not just a query habit |
| Confidence on edges | `claimed` and `uncertain` are stored on the ATTRIBUTED_TO edge | Confidence belongs to the link between an event and a group, not to the group |
| Derived cross-event links | SAME_ACTOR_NEARBY, SAME_SOURCE, SAME_MO_LOCAL, FOLLOWED_BY, SIMILAR_TO; each stores rule, strength and evidence | Every link can explain why it exists, which answers "why are these linked?" |
| Same-actor window | 30 days, with gap_days stored on each edge (236 pairs within 7 days, 632 within 30, 1,446 within 90) | Captures campaign waves without a flood of loose links; other windows stay queryable |
| Shared sources link events | 411 citations are shared by 2 or more events, covering 664 events (40%); SAME_SOURCE uses citations shared by 2 to 10 events (none exceeds 7, so nothing is excluded) | Reaches the 80% of events with an unknown actor |
| GTD related is evaluation only | GTD_RELATED pairs are never used to build links, retrieve results or train models | Prevents a circular evaluation |
| `multiple` is a property only | Not used as a link rule or model feature | It is tied to GTD's own relatedness judgement |
| Rule parameters | Windows, thresholds and validator limits live in dictionaries in src/config.py (GRAPH_RULES, CLUSTER_RULES, VALIDATOR_RULES, FAST_DEFAULTS) | Tuning never means rewriting rules |
| Placeholder organisations | "Not Applicable" and "Civilian(s)" create no TargetOrg node | They mean no organisation, and would form false hubs (140 events) |
| Organisation aliases | Spelling variants of the same organisation are merged (MQM, MQM-H, ANP, PPP, police) | Prevents one organisation being split across nodes and losing links |
| Rebuildable graph | `build_graph.py --reset` rebuilds the Phase 3 and 4 graph (running it twice gives identical counts). The Phase 5 steps (embed_graph.py, similar_links.py, cluster_events.py) and components.py rerun on top of it, and check_graph.py verifies the result | Reproducibility. The reset also removes embeddings, SIMILAR_TO and clusters and leaves components.json stale, so the order matters |
| Source links reach the unknown actors | 607 SAME_SOURCE links connect 524 of 1,338 unattributed events (39%) | The cross-event value for the 80% with no named group |
| Fair evaluation of GTD pairs | GTD_RELATED is tested against text similarity alone, not against source or actor links | 115 of 118 GTD pairs are already linked by shared sources or same actor, so those links would make the test too easy |
| Area extraction method | Rule-based extractor with a gazetteer (names seen in 2+ events). GLiNER and a rules-then-GLiNER hybrid were evaluated and not used | One-shot test on 30 events: rules precision 0.95, recall 0.77 (0.95 on recurring places); GLiNER 0.95 / 0.69; hybrid identical to rules |
| Area definition | One primary Area per event at town or neighbourhood level. Sub-areas that roll up are kept as Localities. Recurring named facilities (consulate, embassy, dockyard, headquarters, airport, airbase, cantonment) count as Areas; roads, districts and police stations do not | Matches how the text names places and what can link events |
| One-event names are not Areas | A name seen in only one event does not become an Area node | It cannot link events; most remaining misses are one-off places |
| Area evaluation protocol | 60-event development set and a separate 30-event test set scored once; text-only labels by the author (single annotator) | Avoids tuning on the test set. Known limits: small sample, one labeller |
| Area roll-ups | A hand-written map folds sub-areas into their town (for example Mominabad into Orangi, Qasba Colony into SITE); places that only look nested (Pirabad and Qasba Colony, Gulistan-e-Jauhar and Gulshan-e-Iqbal) stay separate | Decided by the author from local knowledge; the text alone cannot tell nested from neighbouring |
| Districts and roads are not Areas | Karachi East, Central, South and West, and road names, are ignored | Too coarse or too linear to link events |
| Ambiguous names get no Area | "Bilal Colony" (two different places) is excluded | A shared name would create false links |
| Late extractor changes | Aliases, roll-ups, bare-location handling, the road and district exclusion and the two-level model came after the test set was scored | The test numbers describe the earlier version |
| Two-level places | Area (town level) is used for linking and counting; Locality (specific sub-area) is kept on every event and shown in detail views | Linking needs coarse groups, but users must still learn exactly where an event happened |
| FOLLOWED_BY forms chains | Each event links to the next event in the same Area if it comes within 7 days, not to every event in the window; the longest chain has 13 links, from 20 January to 24 February 2014 | Avoids tangles of links and supports questions about escalation sequences |
| SAME_MO_LOCAL rule | Same Area, same attack type, weapon type and target type (Unknown never counts), within 30 days; a same_locality flag marks events in the same locality (184 links) | Finds repeated methods in the same place |
| Chronology uses dates, not IDs | Ordering and time windows use the date fields; the eventid is only an identifier | GTD IDs can disagree with the date fields (event 201402100070 is dated 2014-02-08) |
| Embedding input | `summary_clean` only, embedded with all-MiniLM-L6-v2 and normalised to unit length; cached in `data/processed/event_embeddings.npz` with the event IDs saved beside the vectors | The longest summary is 217 word-pieces against a 256 limit, so nothing is truncated. Unit length makes cosine a dot product, and the IDs prevent vectors drifting out of row order |
| Duplicate records | The 9 `dup_group` pairs (identical `summary_clean`) are excluded from SIMILAR_TO before ranking; the events stay in the graph | Identical text scores 1.0 whether the pair is a twin record or two incidents with templated wording, so the link reflects the wording and not a cross-event finding. Masking before ranking keeps each event's 5 slots for real neighbours. Cost: the templated-wording incidents lose a similarity link; actor, source and method links can still connect them |
| SIMILAR_TO rule | Top 5 embedding neighbours by raw cosine, cut-off 0.85, kept only when mutual (each event is in the other's top 5). 928 links, 784 events (47%), maximum 5 links per event | Random pairs reach 0.70 at their 90th percentile, so low cut-offs link unrelated events. Without the mutual rule, generic texts became hubs (maximum 40 links, 86 events above 10); a cap of 10 was arbitrary and kept the generic links |
| SIMILAR_TO properties | `strength` (raw cosine), `gap_days`, `same_area` (only when both events share an Area), `rule`, `evidence` | Embeddings capture pattern, not campaign. Time and place stay filterable at query time instead of adding a second threshold. Only 13% of links are within 30 days and 11% in the same Area |
| Cut-off set without GTD_RELATED | 0.85 came from the score distribution and a manual read of sampled pairs | Keeps the GTD pair test uncircular |
| GTD_RELATED test result | One run, text similarity only (111 pairs with different text): mean percentile rank 0.968 among all pairs, median 0.997; 57% of pairs above the 0.85 cut-off, 50% linked by SIMILAR_TO | The baseline is all pairs, which includes different years and attack types, so the rank is easier to reach than chance suggests. Small sample, one run |
| Clustering | UMAP to 5 dimensions, then HDBSCAN (minimum cluster size 10): 31 clusters, 20% noise. A separate 2-D UMAP is used only for the map | Clustering is more reliable in a middle-dimensional space than in 2-D. HDBSCAN chooses the number of clusters itself and leaves one-off events as noise |
| Clusters are a property, not a link | `Event.cluster` is an integer, left unset for noise. Clusters create no edges | A cluster says an event is of a type, not that two events are connected. Applies "Unknown is not a link" to noise |
| Clusters overlap the GTD fields | Most clusters are 94 to 100% a single weapon type. They are kept as a theme grouping, mainly for the clusters that split by target or time window (for example police shootings, religious figures, hostage-taking) | Reading the clusters showed the broad split repeats the weapon field, so they are not presented as findings about campaigns |
| Map data lives outside the graph | 2-D coordinates and cluster ids are saved in `data/processed/event_map.json` | Keeps display data out of the graph; the app serves the file directly |
| Cluster numbers are unstable | Cluster ids change if parameters or library versions change; no query may hard-code one. Naming clusters is left to Phase 8 | Names should be chosen after seeing how the QA layer uses them |
| Severity | Victims killed (`nkill` − `nkillter`), then victims wounded (`nwound` − `nwoundte`). Unknown is not zero: events without `nkill` are skipped, and a missing perpetrator count means the total is used and flagged | GTD totals include attackers. In 2016-2020 the third event by raw `nkill` had only attackers killed |
| Vector search syntax | `db.index.vector.queryNodes` is used in `embed_graph.py` and in queries Q14 and Q15 of the query library. Neo4j deprecated it in 2026.04 in favour of the `SEARCH` clause. It still works on 2026.09; migration is planned after the core app works | A deprecation warning appeared on the rebuild |
| Event ids are internal | Users never type or see event ids. Queries return ids in underscore columns, which the app removes. Events are reached by description, previous results or graph clicks | Ids mean nothing to users and expose the database |
| Relative dates | "Last N years" counts back from the end of the data (2020-12-22), and the answer says so. Requests wholly outside 2000-2020 are refused with a reason | Counting from today would return nothing |
| Link windows | `SAME_ACTOR_NEARBY` and `SAME_MO_LOCAL` answer up to 30 days, `FOLLOWED_BY` up to 7. Longer windows use computed queries (Q3b, Q4b) | Stops a longer window being silently cut to 30 days |
| Coordinated attacks | Q5 returns the gap, same area, shared sources and GTD's `multiple` flag for display, and defines no "coordinated" rule | There is no independent rule, and `multiple` stays display-only |
| Attribution labels | claimed, suspected, and "attributed, not flagged suspected" | GTD has no "confirmed" flag |
| Base-model bake-off | Candidates: Qwen2.5-Coder-3B, Qwen3.5-4B, Phi-4-mini, Gemma 4 E4B. Hard filters: peak VRAM at most 5.5 GB in 4-bit with the real prompt plus 256 output tokens on the 6 GB GPU; no NaN or inf loss in the first 300 fp16 steps on Kaggle. One recipe for all (rank 16, alpha 32, learning rate 2e-4, 2 epochs, seed 42, same pairs), no per-model tuning. Winner: highest dev execution accuracy after fine-tuning. A model with a larger 4-bit size must win by at least 5 points; smaller gaps go to the lighter one | One recipe means gaps come from the model, not the tuning. Dev has 60 answerable questions, so 5 points is 3 questions and is inside the noise: a tie-break rule, not a significance test |
| Metrics | Primary: execution accuracy, the share of answerable questions whose query returns the same set of rows as the gold query on the gold's columns (order ignored; for top-N questions the same N events, and gold must have no tie at the cut). Secondary: valid-query rate (CYPHER outputs that pass the validator and run, over all CYPHER outputs); refusal reported as two numbers, refusals made when they should and questions wrongly refused. FAST counts only with the right query and group | One refusal accuracy would hide over-refusing |
| Two lanes | Fast lane: library queries run with app-filled parameters. Open lane: model-written Cypher in a read-only transaction, no CALL. The model routes and replies CYPHER, REFUSE or FAST. At the start Q8, Q10, Q14 and Q15 are FAST (FAST: Q8 with at least 1 event in context; FAST: Q10 with at least 2; FAST: Q14 with at least 1; FAST: Q15 followed by a group from the list); Q0b (the event finder, which also answers ranking questions), Q1 to Q7, Q9 and Q11 to Q13 are open lane. The app sets k, min_cosine and limit, and Q10 runs the component check first (see the Path bound row). Validator: LIMIT required and at most 100 (50 for lists); 10 s timeout; variable-length patterns only on FOLLOWED_BY, directed, with an upper bound of at most 6; CONTAINS only on location, summary_clean and TargetOrg name; FAST accepted only as Q8, Q10, Q14 or Q15, and Q15 only with a group in the list; Neo4j notifications (for example 03N90) are not failures, only errors are | Measured on the dev PC: shortestPath between five pairs (two from the highest-degree event at distance 6 and 7, one at distance 21, two hubs 4 apart, and a cross-component pair) took 22 to 265 ms on the first run and 4 to 9 ms on the second. An earlier single figure of 4,327 ms was not reproduced (cold start suspected, not proven). 3-hop expansion from the 5 busiest events reached 78 to 200 events and 5,262 to 6,558 paths. Counting every path of up to 6 links from the busiest event (16,765,630 paths) took 3.7 s, and a sorted top 50 over paths of up to 5 links took 0.9 s, so enumeration needs no extra rule. The 10 s timeout stays as the ceiling, and a query that hits it returns a plain "too broad" message. Re-time these on the demo PC. Q8 and Q10 are FAST from the start because they need only event context and no text parameters, and open-lane patterns over the undirected link union return the same event many times and loop back to the start event (seen in the 5-hop test); Q8 is also the hardest library query for a small model to write (expected, not measured). The open lane never writes vector search, so moving to SEARCH cannot break training pairs |
| Dev and test sizes | Dev: 95 questions (60 answerable, 5 phrasings for each open-lane query among Q0b, Q1 to Q7, Q9 and Q11 to Q13; 20 FAST, 5 each for Q8, Q10, Q14 and Q15; 15 should-refuse, including questions about "that event" with events=0). Test: 60 questions (40 answerable, 10 FAST, 10 should refuse) | Enough to rank models roughly; test intervals stay wide (see the Test set row) |
| Test set | Questions from at least 3 people other than the developer, none from an LLM, who get one paragraph describing the data and not the library or the prompt. The developer sets the CONTEXT line (events=N) for each question from its wording before the first run. Gold written before the first run. No question dropped or edited after any model sees the set. Any training question with MiniLM cosine of 0.85 or more to a dev or test question is removed, and the count is reported. Scored once | With 40 answerable questions a 95% interval on accuracy is about plus or minus 12 points, so only large gaps mean anything; results report intervals |
| Fine-tuning success rule | On the test set, fine-tuned execution accuracy beats the untrained model's by at least 15 points and the paired difference passes a one-sided exact sign test at p below 0.05 (only questions where exactly one model is right). Prompted Gemini with 8 fixed few-shot examples (same prompt file and validator, model name and date recorded) is reported whichever way it falls and does not decide pass or fail. If the rule fails, the report says fine-tuning did not help | 15 points is 6 net questions of 40; the sign test is the stricter condition: 9 wins to 2 losses passes, 8 to 2 does not |
| Promotion to FAST | After the Gemini baseline and again after the fine-tune, any open-lane query among Q0b, Q1 to Q7, Q9 and Q11 to Q13 with fewer than 4 of its 5 dev phrasings correct by execution is promoted to FAST. Dev set only. The lane map is frozen before the test run. A promoted query that needs text parameters is written FAST: Qn key=value, with the library's parameter names; the validator checks each value (names against the lists, dates in range, numbers within limits). Q8, Q10, Q14 and Q15 are already FAST and take only event context or a group. The whitelist widens in the same change as the prompt and the training pairs | A query the model cannot write reliably is better served by the library. Changing the whitelist without the prompt and pairs would make the model emit forms the validator rejects |
| Training data | About 10 to 15% of pairs are FAST examples (Q8, Q10, Q14, Q15). Every pair carries the CONTEXT line (events=N) | The model must learn when to route, and the context line is what it routes on |
| Place-fallback test | Run first with hand-written Cypher, no model: 10 road or landmark names taken from events with no Area, chosen before looking at results, up to 5 events each. Correct = the event text names the place as where the incident happened (a mere mention does not count), labelled by the developer. Keep the fallback if at least 80% of returned events are correct and at least 40 events came back (the 40-of-50 rule). 5 invented names must each return no rows. If it fails, names in neither list are refused | The fallback pattern is about the data, not the model, so it can be tested before any GPU work. One labeller, as in the area evaluation |
| Scope guard and link scorer | Guard: in, second priority after the headline model. Logistic regression on MiniLM embeddings first; DistilBERT only if it beats it by at least 5 points of accuracy in 5-fold cross-validation on the training questions. Pass: on the test set at least 8 of 10 should-refuse questions caught and at most 5 of 50 other questions blocked. Link scorer: out of Phase 6 | The guard is a second check on refusals and the only place DistilBERT could earn its slot. The link scorer needs about 200 hand-judged links and was the first cut |
| Names outside the lists | Places not in the Area or Locality lists are searched in location and summary_clean with CONTAINS, and the query returns 'text' AS place_match. Organisations (380, not listed) are matched on the TargetOrg node with CONTAINS on one distinctive word, returning 'text' AS org_match and o.name AS org_name. Groups not in the 39 are refused. Bare "Taliban" is refused with a question; ISIS and Daesh map to the Khorasan Chapter of the Islamic State and the answer names the full group. "Karachi" or "Sindh" alone is not a place filter | Roads, courts and landmarks are what people type and cover the 26% of events with no Area. Attribution comes only from the ATTRIBUTED_TO edge, so groups get no text fallback. The place fallback is tested before use (Place-fallback test row) |
| Open-lane query conventions | Filter on the Event properties attack_type, weapon_type and target_type; use the type edges only to group across events (Q6, Q11). Severity ranks by victims killed, then victims wounded, with coalesce on wounded (Cypher sorts null first in descending order). Event ids are returned only in underscore columns; a specific event is $ref, $ref_a or $ref_b | These match the verified library queries |
| Prompt freeze | src/prompts/schema_prompt.txt is the one prompt used by the training pairs, the Gemini baseline, the bake-off and the demo. It is frozen at commit ee54881 (tag prompt-freeze-v1), before the first training pair is generated. Any later edit means regenerating the pairs and re-running the dev scores | The model learns this exact text |
| Path bound for Q10 | Q10 keeps *..6, and VALIDATOR_RULES["max_path_hops"] equals it. Measured on the five link types (src/check_diameter.py): 514 components (413 isolated events, largest 984), longest shortest path 21; of 483,936 connected pairs (35% of all pairs; the other 65% are in different components), 165,003 (34%, or 11.9% of all pairs) are within 6 hops and 68,926 at exactly 6; 96,077 within 5, 411,472 within 10. Neo4j agreed at the boundary, including from the highest-degree event: a distance-6 pair returned 6 hops, distance-7 and distance-21 pairs returned no rows. Component ids are saved after the build (src/components.py) with the event and link counts, and loading them fails if the counts no longer match the graph. Different components answer "no link of any length"; the same component with no path in 6 answers "no chain of up to 6 links, though the two events are connected through a longer chain". Never "not connected" unless the components differ | Lowering the bound would lose 68,926 pairs, and longer chains explain little. The component check chooses the wording and skips the query for cross-component pairs; it is not needed for speed (no-path queries took 4 to 32 ms). Re-time the four pairs on the demo PC |
